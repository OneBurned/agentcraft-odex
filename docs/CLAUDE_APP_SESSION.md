# Подключение к сессии Claude Desktop Code

Исследование t56, 2026-10-10. **Вариант Б реализуем частично:** читать сохранённую
историю и наблюдать зарегистрированный процесс можно. Полный внешний клиент
существующей Code-сессии — отправка, поток событий, разрешения и подтверждённая
остановка — в проверенных интерфейсах не подтверждён. Текущую блокировку общего
разговора AgentCraft снимать нельзя.

Под «вариантом Б» здесь понимается: приложение владеет единственным исполнителем,
а мост и Minecraft подключаются к нему как клиенты. Это отличается от восстановления
истории в новом процессе и от управления сессией, которую запустил сам SDK.

токены, cookies, ключи и содержимое личных разговоров не читались.

## Ответы на пять вопросов

| Возможность извне для уже открытой Code-сессии | Вывод | Доказательство и предел проверки |
| --- | --- | --- |
| 1. Отправить сообщение | **Частично** | Встроенная межсессионная переписка существует, но это инструменты другой Claude-сессии, не обнаруженный внешний API моста. `--desktop` с текстом отказал; `-p --resume` выполнил отдельный ход с той же историей, а интерактивный `--resume` создал второй процесс. Это не доказательство доставки в исполнитель приложения. |
| 2. Читать новые сообщения и шаги | **Частично** | `getSessionMessages(id, {dir})` вернул тестовые user/assistant сообщения и последующий ответ отдельного процесса. Это чтение записанного transcript, не подписка на события Desktop. Поток `stream-json` проверен только у собственного CLI/SDK-процесса. |
| 3. Работает / ждёт ответа или разрешения / свободна | **Частично** | `claude agents --json --cwd <test-dir>` показал процесс приложения как `kind: interactive`, `status: idle`, с PID и UUID. Переходы Desktop через running/ожидание разрешения в живом UI не проверены. SDK даёт события и обработчик разрешений своему владельцу, не внешнему наблюдателю приложения. |
| 4. Прервать ход с подтверждением | **Нет подтверждённого внешнего управления Desktop** | `claude stop <test-id>` → `No job matching`. Внутри приложения есть `stop_session`/`interruptSession`, но внешний вызов не проверен. SDK `query.interrupt()` дал receipt и терминальный результат только для отдельно запущенного SDK-процесса. |
| 5. Определить открытие / закрытие | **Частично** | Реестр `agents --json` и проверка PID подтверждают живой зарегистрированный исполнитель. Закрытие CLI удалило именно его строку, Desktop-процесс остался. Transcript/getSessionInfo сохраняются и после окончания процесса; они не доказывают, что сессия открыта. Закрытие вкладки Code и его соответствие реестру не проверены. |

«Нет подтверждённого» не означает отсутствие внутренних возможностей приложения.
Это отсутствие проверенного пригодного для AgentCraft внешнего контракта в данных
версиях и границах исследования.

## Воспроизводимые наблюдения

### E1. Отдельная история и поток CLI

В пустой тестовой папке создан UUID выше. Вызов без инструментов и пользовательских
настроек, с бюджетом проверки:

```powershell
$cli = 'C:\Users\GB\.local\bin\claude.exe'
$testId = '251a6cca-4cda-4ee1-8de9-1c0aeae6c6bb'
& $cli -p 'Reply exactly T56_SEED_OK. Do not use tools.' `
  --session-id $testId --output-format stream-json --verbose `
  --include-partial-messages --tools '' --strict-mcp-config `
  --mcp-config '{"mcpServers":{}}' --setting-sources '' `
  --permission-mode default --max-budget-usd 0.25
```

Exit 0; результат `T56_SEED_OK`. Получены `system/init`, `system/status`,
`stream_event`, `assistant`, `rate_limit_event`, `result/success`.
Это подтверждает поток **запущенного нами** CLI, не чтение потока приложения.

### E2. Штатное открытие в Code

`--desktop` с перенаправленным stdout завершился с exit 1: требуется интерактивный
терминал. При повторе в PTY текстовый prompt также был отклонён:

```text
--desktop doesn't take a prompt yet. Run `claude --desktop`, then type it in the app.
```

Без prompt, в PTY:

```powershell
& $cli --desktop --resume $testId
```

Exit 0:

```text
Opening session 251a6cca-4cda-4ee1-8de9-1c0aeae6c6bb in Claude Desktop
```

После этого `agents --json --cwd <test-dir>` вернул одну запись:

```json
{"pid":15304,"kind":"interactive","sessionId":"251a6cca-4cda-4ee1-8de9-1c0aeae6c6bb","status":"idle"}
```

PID подтверждён через `Get-CimInstance Win32_Process`; его родитель — процесс
приложения, путь исполнителя указывает на bundled CLI 2.1.295. Вывод CLI и появление
процесса подтверждены; визуального осмотра вкладки не было: доступное средство
управления компьютером в этой сессии не поддерживает native apps.

### E3. Resume не обеспечивает одного владельца

Пока PID 15304 был жив, выполнен `-p --resume $testId` с теми же ограничениями E1,
`--output-format json` и prompt `Reply exactly T56_SECOND_CLIENT_OK. Do not use tools.`
Получен exit 0, `result: T56_SECOND_CLIENT_OK`, тот же `session_id`.

Затем интерактивный `claude --resume $testId` в PTY открыл историю, а реестр показал
**два** живых процесса с одинаковым UUID: Desktop PID 15304 и CLI PID 22636.
У обоих `kind: interactive`, `status: idle`. Командой `/exit` закрыт только созданный
нами CLI; PID 22636 исчез, PID 15304 остался. Ни отказа от конкурирующего открытия,
ни передачи владения в этом эксперименте не произошло.

Следствие: успешный `--resume` нельзя считать ни attach к приложению, ни защитой
от двух писателей. Нельзя заменять им `conversation-lock.json`. Проверка не
устанавливает, обновил ли Desktop свою историю в памяти после записи второго CLI.

### E4. Новые фоновые команды не управляют этой Code-сессией

```powershell
& $cli attach $testId
& $cli logs $testId
& $cli stop $testId
```

Каждая команда вернула `No job matching` для тестового UUID, хотя `agents --json`
видел живой Desktop-процесс. Справка установленного CLI относит эти команды к
background sessions. `agents --json` перечисляет также interactive sessions;
наличие записи не означает поддержку `attach`/`stop`.
Справка `--bg --resume` предупреждает, что для уже работающей сессии может создать
копию. Этот путь не использовался и не решает требование единственного разговора.
Описание команд: [CLI reference](https://code.claude.com/docs/en/cli-reference),
[agent view](https://code.claude.com/docs/en/agent-view).

### E5. Чтение transcript через публичный SDK

```js
const info = await getSessionInfo(testId, { dir: testDir });
const messages = await getSessionMessages(testId, { dir: testDir });
```

SDK 0.3.286 прочитал именно тестовый каталог: сначала пару user/assistant из E1,
после E3 — четыре сообщения с обоими маркерами. `info` содержит `sessionId`, `cwd`,
`lastModified`, `fileSize`, заголовок и прочие метаданные; поля live-статуса нет.
Сохранять cursor по UUID и опрашивать transcript можно, но это не гарантирует
появление каждого шага немедленно, доставки незаписанного текста или определения
ожидания разрешения. Документированное
[resume и хранение истории](https://code.claude.com/docs/en/agent-sdk/sessions)
не обещает attach к владельцу Desktop.

### E6. Подтверждённое прерывание собственного SDK-процесса

Отдельный UUID `a5e2d797-9999-46b4-be9f-368db68bc09b`, SDK 0.3.286 с
`pathToClaudeCodeExecutable` на CLI 2.1.291. `query()` получил открытый async input,
`tools: []`, пустой strict MCP, `settingSources: []`, `permissionMode: default`,
`includePartialMessages: true`, `maxBudgetUsd: 0.25`.
Prompt просил печатать числа; на первом `content_block_delta` вызван
`await query.interrupt()`, затем прочитан terminal result и закрыт query.

```json
{"interrupted":true,"receipt":{"still_queued":[]},"result":{"subtype":"error_during_execution","is_error":true,"stop_reason":null},"saved":true,"messageCount":2}
```

Ошибка terminal result здесь ожидаема при прерывании и не обозначает успешное
выполнение задания. Подтверждение запроса и завершение хода — разные сигналы;
receipt со списком очереди нельзя трактовать как автоматическую отмену всех
следующих сообщений. Наличие этого метода у `Query` **не даёт Query-handle**
чужого процесса Desktop. См. [поток SDK](https://code.claude.com/docs/en/agent-sdk/streaming-output)
и [обработка разрешений SDK](https://code.claude.com/docs/en/agent-sdk/user-input).

## Интерфейсы самого приложения

Read-only просмотр таблицы ASAR и ограниченных фрагментов установленного JS обнаружил:

- `index.chunk-CJzkue6W.js`: операции `LocalSessions.sendMessage`, `interrupt`;
- `index.chunk-1xGiXs9t.js`: инструменты `send_message`, `stop_session`, создание
  MCP через `createSdkMcpServer`; остановка может отказать при удерживаемом вводе пользователя;
- `index.chunk-D7ye_MQA.js`: состояние `awaiting_permission`, `running`, `needs_input`,
  операции `interruptSession` и работа с объектом текущего query;
- `index.chunk-EzXl5k4A.js`: регистрация Electron IPC с проверкой sender frame.

Это внутренние операции и встроенные инструменты, а не обнаруженная общедоступная
named-pipe/HTTP-служба для AgentCraft. Их извне не вызывали; проверки sender,
аутентификации и разрешений не обходили. Имена chunks и методы — наблюдения этой
сборки, не API для реализации. Не патчить ASAR и не внедряться в renderer для
получения доступа к этим операциям.

Официальная [документация Desktop](https://code.claude.com/docs/en/desktop#work-across-sessions)
подтверждает встроенную работу Claude с другими Code-сессиями. Она не документирует
для стороннего локального клиента аналог Codex `send_message_to_thread/read_thread`.
Отсутствие такого описания вместе с проведёнными проверками ограничивает вывод;
это не доказательство отсутствия всех возможных интерфейсов будущих версий.

## Альтернативы и стабильность

| Путь | Применимость и риск |
| --- | --- |
| SDK transcript API | Публичный интерфейс для сохранённой истории. Уже используется в `foreman/src/claude-conversation.ts`. Нужны точные UUID/каталог, дедупликация, обработка неполной записи; не выдавать stale-данные за live-статус. |
| `agents --json` | Публичный CLI-интерфейс. Полезен для диагностики процесса; нужны проверка PID/времени запуска и совместимости версии. Нет доказательства равенства «нет строки» и «вкладка закрыта». |
| SDK `query`, stream, interrupt | Подходит, когда мост владеет исполнителем. Не заменяет внешний клиент Desktop. Обновления требуют проверки terminal result и interrupt capabilities. |
| Встроенная межсессионная переписка | [Документирована](https://code.claude.com/docs/en/cross-session-messaging), включая Windows named pipes. Сообщение имеет происхождение от другого агента и не является согласием пользователя; возможны hold/refuse. Это не команда паузы и не полный поток работы. Raw-протокол pipe в этом исследовании не вызывался. |
| Channels | [Research preview](https://code.claude.com/docs/en/channels): MCP может доставлять события в уже работающую сессию и принимать ответы инструментом. Требуются явная настройка и проверка поддержки именно Desktop Code. В t56 не устанавливались; полного управления ходом этот факт не доказывает. |
| Remote Control | [Официальный путь](https://code.claude.com/docs/en/remote-control) к локальной сессии из Claude web/mobile. Это не найденный публичный API стороннего моста. Включение и сетевой доступ в тесте не менялись. |
| Managed Agents API | [События и interrupt](https://platform.claude.com/docs/en/managed-agents/events-and-streaming) относятся к отдельным управляемым облачным сессиям. Их ID/API нельзя приравнять к локальному UUID Code. Не проверялся и не нужен для доступа к личной сессии. |
| Внутренний Desktop IPC | Высокий риск обновлений, нет проверенного внешнего контракта. Не использовать как основу переносимого мода. |

## Рекомендация и следующий шаг

Сохранить нынешнее эксклюзивное владение Claude-разговором и штатную передачу через
`Open-Klava-Code` / `Return-Klava-To-Game`. Это ограничение AgentCraft защищает от
двух процессов с одной историей; эксперимент E3 показывает, почему нельзя полагаться
только на защиту CLI.

В рамках отдельной согласованной задачи можно исследовать **Channels для обмена
сообщениями**, не обещая полной замены транспорта. Для полноценного варианта Б нужны:

1. Поддерживаемый способ получить клиентский handle существующей Desktop-сессии,
   привязанный к конкретному UUID, без запуска второго исполнителя.
2. Подтверждение приёма сообщений с идентификаторами и защитой от повторной отправки.
3. Поток с восстановлением cursor и проверенные состояния: ход, вопрос пользователю,
   разрешение, idle, disconnect. Отсутствие событий означает unknown, не idle.
4. Прерывание с подтверждением завершения хода и судьбы очереди сообщений; никаких
   автоматических ответов на permission prompts вместо пользователя.
5. Проверка закрытия, повторного открытия и падения приложения. Потеря PID сама по
   себе не разрешает второму процессу захватить историю.

После появления подходящего API нужен отдельный испытательный стенд: сообщение во
время работы, pause/resume/stop, ожидание разрешения, reconnect, повтор доставки,
закрытие UI и перезапуск приложения. До этих проверок не объявлять паритет с Codex.

## Границы результата

Подтверждены команды, версии, запись/чтение двух тестовых маркеров, два процесса с
одним UUID и interrupt собственного SDK-процесса. Не проверены визуальное обновление
Code, его живые permission prompts, закрытие вкладки и внешний interrupt Desktop.
Продуктовый код и конфигурация моста не менялись; Minecraft не запускался,
push/deploy не выполнялись. SDK query и дополнительный CLI завершены. Тестовая
Code-сессия оставлена idle: её можно закрыть в приложении; приложение целиком и
личные сессии не останавливались. Локальные краткие результаты находятся в тестовой
папке (`seed-evidence.json`, `desktop-launch.json`, `second-client.json`,
`sdk-interrupt.json`); необходимые наблюдения перенесены в этот документ.
