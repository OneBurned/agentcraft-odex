2026-10-10. По отдельному согласию пользователя выполнен тест терминального CLI
после [исследования Desktop](CLAUDE_CHANNELS.md). **Обмен сообщениями и продолжение
той же истории в терминале подтверждены.** Это стенд собственного MCP-канала;
игровой мост Foreman к нему ещё не подключён, личный разговор Клавы не перенесён.

наблюдения стенда, не гарантия задержки или доставки.

## Стенд и воспроизведение

Папка: `%LOCALAPPDATA%\Temp\agentcraft-t62-EoiKsv`.
Только тестовый UUID: `20326ab9-07f4-441e-84e4-26d6e05bf177`.
Сервер `probe.mjs` и `.mcp.json` описаны в [Desktop-исследовании](CLAUDE_CHANNELS.md).
`launch.mjs` передаёт аргументы через Node `spawn` массивом и использует stdio PTY:

```text
claude --resume <test-UUID> --name "AgentCraft Channels test"
  --dangerously-load-development-channels server:t62probe
  --strict-mcp-config --mcp-config .mcp.json --setting-sources project
  --tools "" --permission-mode default --allowedTools mcp__t62probe__reply
```

Это параметры второго запуска и сохранённого launcher. Первый запуск не задавал
`--permission-mode`, поэтому CLI показывал Auto; второй явно использовал default
и показывал Manual. В обоих случаях builtin tools отключены, strict MCP разрешает
только тестовый сервер, а project settings сохраняют 34 запрета `desktopDeniedTools`.
Единственное явно разрешённое действие модели — запись синтетического reply в
локальный журнал. Permission relay и обход разрешений не включались.

На первом запуске подтверждены доверие к созданной нами временной папке и режим
локальной разработки канала. При повторном запуске development-подтверждение
потребовалось снова. Нельзя выдавать такой запуск за готовый фоновый сервис без
участия пользователя. Настройки личного рабочего места Клавы не изменялись.

Внешний процесс трижды передал один и тот же объект через `inbox.json`:

```json
{
  "event_id": "t62-event-1",
  "content": "Reply T62_CHANNEL_OK to this synthetic event using reply."
}
```

Сервер проверяет фиксированные ID и содержимое, переносит прочитанный файл в
`consumed-<time>.json`, отправляет notification и ждёт tool reply. Здесь нет
сетевого порта или приёма произвольных пользовательских задач. Журнал
`channel-evidence.jsonl` различает `notification_written` и `reply`: только второе
событие доказывает получение ответа в этом тесте.

CLI PID: `34528`, затем `13464`; MCP PID: `30696`, затем `36204`.
SDK `getSessionMessages` для тестового UUID вернул 19 записей, в том числе три
сообщения с `origin.kind: channel`, tool calls/results и ответ после resume.
У всех записей один `session_id`. Нормализованный результат сохранён в
`cli-evidence.json`, без ключей, токенов и личных сообщений. Файлы стенда оставлены;
процессы завершены. Для нового прогона использовать новую папку и UUID: текущие
счётчики и ответы относятся к зафиксированному эксперименту.

## Что ещё нужно перед подключением к игре

Рабочая схема для следующего этапа: Minecraft → Foreman → собственный MCP-канал
→ постоянно открытый терминальный Claude Code; ответ возвращается через tool.
В этом варианте исполнитель живёт в терминале. Проверка не подтверждает Channels
для сессии, запущенной внутри Desktop, и не отменяет выводов t62 о Desktop.

До миграции нужны:

1. Сохраняемые ID сообщений, состояния доставки и защита от повторной отправки и
   показа ответа. После сбоя между отправкой и записью receipt нельзя молча
   повторять задачу: её выполнение могло уже начаться.
2. Привязка канала к конкретному агенту, профилю, UUID и единственному владельцу
   процесса. Сохранённая история не является блокировкой конкурирующего запуска.
3. Проверка событий при занятом ходе, ожидании пользователя/разрешения и потере
   MCP-соединения. Восстановление после аварии и события во время offline здесь
   не проверялись; обычный `/exit`/resume их не заменяет.
4. Отдельное управление Pause/Stop с подтверждением реальной остановки. Здесь
   завершался только свободный тестовый CLI; прерывание работающей задачи не
   проверялось. Отправка текста «стоп» для этого недостаточна.
5. Проверка правил Клавы с её рабочими инструментами и затем отдельная миграция
   личной сессии. Совпадение массива deny не является проверкой всех permission
   сценариев на реальных подключённых инструментах.

Это **успешный прототип обмена сообщениями**, не установленное обновление мода.
Проверки подтвердили три reply, два initialize, три channel-записи в одной истории,
ответ после resume и сохранение массива deny. Начальная проверка ответа ожидала
пробел между маркерами; чтение source transcript показало перенос строки. Проверка
исправлена на фактическую структуру текстового блока и точный ответ с `\n`.
Продуктовые тесты не запускались: код продукта не менялся. Push/deploy не выполнялись.
