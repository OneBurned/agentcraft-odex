# Claude Channels и сессия Desktop Code

Исследование t62, 2026-10-10. **Рекомендация для текущего AgentCraft: не внедрять
Channels как транспорт к Desktop Code.** Проверенный запуск через `--desktop`
отвергает оба флага Channels, а в осмотренных настройках приложения включение
каналов не найдено. Это отрицательный результат проверки доступных путей, а не
доказательство отсутствия всех внутренних возможностей Claude.

Полный вариант Б из [CLAUDE_APP_SESSION.md](CLAUDE_APP_SESSION.md) не подтверждён.
Даже вариант «только сообщения в Desktop» пока не прошёл начальный этап — включение
канала. Снимать блокировку общего разговора или менять Pause/Stop на отправку
текста нельзя. Продуктовый код в этом исследовании не изменён.

Отдельно, после согласия пользователя на терминальный вариант, проверен
[CLI-прототип](CLAUDE_CHANNELS_CLI.md): событие, reply, повтор ID и история после
resume. Он работает в терминале; выводы этого документа относятся к Desktop.

## Семь критериев

Здесь «нет» означает отсутствие подтверждённой возможности для нашего подключения
к Desktop. «Частично» отделяет документированный контракт от живой проверки.

| Критерий | Вывод | Доказательство и граница |
| --- | --- | --- |
| 1. Штатное включение собственного канала в Desktop Code | **Нет подтверждённого пути** | E2: обе версии CLI отвергают development-флаг вместе с `--desktop`; отдельный CLI также отвергает `--channels`. E3: поиск настроек Channels пуст. Минимальная версия Desktop с такой поддержкой не установлена. |
| 2. Внешнее сообщение, receipt, ID, повтор и занятый ход | **Частично: контракт, без живого Desktop-теста** | [Reference](https://code.claude.com/docs/en/channels-reference): уведомление не имеет ACK обработки; запись в stdio не доказывает доставку, возможен silent drop. При занятом ходе события могут объединяться. Сквозной ID/dedup AgentCraft не проверен и не реализован. |
| 3. Ответ, шаги и промежуточный текст | **Частично: контракт, без живого Desktop-теста** | В [Channels](https://code.claude.com/docs/en/channels) описан ответ отдельным tool. Это не подписка на все шаги/текст. В тесте reply не вызывался; ни поток Desktop, ни доставка ответа в игру не подтверждены. |
| 4. Running / ожидание пользователя или разрешения / idle | **Нет подтверждённой полной модели состояний** | В [t56](CLAUDE_APP_SESSION.md) проверен idle в реестре процессов, но не эти переходы Desktop. Отдельный permission relay в Reference не является полной моделью состояния. В t62 он не включался. |
| 5. Прерывание, Pause/Stop с подтверждением | **Нет подтверждённого пути** | В просмотренном контракте Channels не найден interrupt с receipt завершения. Успешный interrupt собственного SDK-процесса из t56 не относится к Desktop. Сообщение «стоп» не доказывает остановку. |
| 6. Закрытие вкладки, рестарт приложения, reconnect | **Нет подтверждённого восстановления** | Канал в Desktop не зарегистрирован; эти сценарии не прогонялись. Ни повторная доставка, ни восстановление cursor, ни сохранение одного исполнителя не доказаны. Личное приложение целиком ради теста не перезапускалось. |
| 7. Сохранение запретов t19 | **Частично** | Временные project settings содержат весь `desktopDeniedTools`; новых разрешений инструментам не добавлено. Поведение deny при активном канале в Desktop не проверено, поскольку канал не запущен. Источник правил: `tools/lib/klava-desktop-settings.mjs`. |

Отсутствие включённого канала остановило живые проверки 2–7. Они не отмечены как
успешные по результатам документации или тестового CLI seed.

## E1. Отдельная тестовая история и конфигурация

В пустой папке создана история командой ниже. Аргументы передавались через
Node `spawnSync` массивом, без shell; `cwd` — тестовая папка.

```text
claude -p "Reply exactly T62_SEED_OK. Do not use tools."
  --session-id 20326ab9-07f4-441e-84e4-26d6e05bf177 --output-format json
  --tools "" --strict-mcp-config --mcp-config '{"mcpServers":{}}'
  --setting-sources project --max-budget-usd 0.25
```

Результат: exit `0`, `is_error: false`, `result: T62_SEED_OK`, ожидаемый UUID.
Сохранён в `seed-evidence.json`. Это проверка отдельного CLI, не Channels.

Затем подготовлен `probe.mjs` со stdio MCP, capability `claude/channel`, одним
инструментом `reply` и локальным журналом синтетических маркеров. Сетевых портов,
доступа к проектам и автоматических событий у стенда нет. Входное событие требует
отдельного файла `inbox.json` с фиксированными тестовыми ID/текстом; файл не создавался.
Permission relay отсутствует. Конфигурация `.mcp.json` только в тестовой папке:

```json
{
  "mcpServers": {
    "t62probe": {
      "command": "C:\\Program Files\\nodejs\\node.exe",
      "args": ["C:\\Users\\GB\\AppData\\Local\\Temp\\agentcraft-t62-EoiKsv\\probe.mjs"]
    }
  }
}
```

`.claude/settings.json`: `disableAllHooks: true`, `permissions.deny` — точная копия
массива `desktopDeniedTools`. Ни `permissions.allow`, ни обхода разрешений нет.
Само наличие `.mcp.json` не включает канал.

## E2. Проверка команды открытия Desktop

В PTY, из тестовой папки, без текстового prompt:

```powershell
$testId = '20326ab9-07f4-441e-84e4-26d6e05bf177'
$cli = 'C:\Users\GB\.local\bin\claude.exe'
& $cli --desktop --resume $testId --dangerously-load-development-channels server:t62probe
```

Exit `1`:

```text
--desktop only opens the Claude Desktop app; it can't be combined with `--dangerously-load-development-channels`.
```

Тот же вызов со встроенным CLI `2.1.295` дал тот же отказ. Проверенный путь:
`%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude-code\2.1.295\d2e29494ec83\claude.exe`.

Дополнительный вызов отдельного CLI:

```powershell
& $cli --desktop --resume $testId --channels plugin:fakechat@claude-plugins-official
```

Exit `1`, тот же текст отказа с `--channels`. Fakechat не устанавливался: отказ
касается сочетания флагов, это не проверка самого плагина. После вызовов
`claude agents --json --cwd <test-dir>` вернул `[]`; журнал канала не появился.
Исполнитель Desktop и MCP-сервер этими вызовами не запущены.

## E3. Осмотр настроек приложения

После первоначального белого окна пользователь открыл Settings → Claude Code.
Настройки прочитаны через Windows Computer Use, включая содержимое ниже видимой
области. Есть General, Code appearance, Appearance, Remote Control, Sessions,
Browser и Pull requests. Поле включения Channels или передачи его launch-флага
не обнаружено. В Search settings введено `channels`: **No matching settings**.
После проверки поисковая строка очищена; переключатели и настройки не изменены.

Remote Control присутствует отдельным параметром. Его наличие не проверяет API
для AgentCraft и не доказывает поддержку Channels. Это возможный предмет другого
исследования, а не выполненный критерий t62.

## Документированный контракт и ограничения

[Channels reference](https://code.claude.com/docs/en/channels-reference) описывает
stdio MCP, `notifications/claude/channel` и отдельный reply tool. Собственный канал
research preview включается development-флагом в интерактивном CLI после
подтверждения; в `-p`/SDK этот флаг игнорируется. Политика организации продолжает
действовать. Этот терминальный путь в t62 не запускался вместо Desktop.

[Desktop](https://code.claude.com/docs/en/desktop) поддерживает обычную MCP-конфигурацию
и project permission rules. Из этого не следует, что каждая MCP capability
доступна в приложении. Документированного аналога флагов Channels в просмотренной
странице Desktop не найдено. Проверка E2 даёт более узкое, но воспроизводимое
доказательство: эти флаги не передаются через наш текущий launcher.

[Channels](https://code.claude.com/docs/en/channels) остаётся research preview с
требованиями к аутентификации и организационному включению. Версии CLI и Desktop
обновляются независимо. Результат нельзя переносить на будущие версии: при новом
официальном способе включения потребуется повторная проверка всех семи критериев.

## Решение для t57 и следующий эксперимент

**Полностью — нет; только сообщения в Desktop — также не подтверждено.**
Причина отказа от реализации t57 сейчас: нет проверенного входа в нужный
исполнитель приложения, а контракт сообщений не закрывает управление ходом.
Текущий разговор и правила передачи владения остаются прежними.

Возвращаться к реализации можно после появления документированного Desktop-входа:

1. В новой пустой папке и отдельной сессии подтвердить регистрацию канала в Desktop.
2. Проверить один event/reply, явное подтверждение обработки, повтор одного ID и
   событие во время занятого хода. Спроектировать сохраняемые ID и дедупликацию.
3. Получить и проверить состояния, подтверждённый interrupt, восстановление после
   потери соединения и единственного владельца истории. Тишина означает unknown.
4. Проверить запреты t19 на подключённых безвредных инструментах и отсутствие
   автоматического подтверждения разрешений. Только затем проектировать продукт.

Если пользователь выберет терминальный CLI вместо владельца в Desktop, это другая
архитектура и отдельный согласованный эксперимент. Успешный терминальный канал
не должен автоматически закрывать критерии Desktop или отменять conversation lock.

## Стенд и проверки Desktop-этапа

На этапе Desktop подготовлены `probe.mjs`, `.mcp.json`, `.claude/settings.json`,
`seed-evidence.json`. Канал тогда не запускался, история содержала только seed.
Позднее этот стенд использован в отдельно согласованном [CLI-тесте](CLAUDE_CHANNELS_CLI.md);
там описаны его сообщения, оставленные файлы и завершение процессов. Для нового
прогона создать новую папку и UUID; не подставлять личную сессию.

Проверены синтаксис стенда, JSON конфигурации, совпадение deny с исходными правилами,
локальные ссылки документации и `git diff --check`. Продуктовые тесты не запускались:
изменены только два документа. Проверки файлов не являются живой приёмкой канала.
Push и установка обновления в исследование не входят.
