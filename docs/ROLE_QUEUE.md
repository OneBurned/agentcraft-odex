# Очередь с назначением агентов

Очередь доступна в исходниках моста и мода с протоколом v2. Сборка или обновление
исходников не обновляют уже запущенный личный мост и установленный мод.

## План и исполнители

Список доски показывает статус задачи, назначенного разработчика и ревьюера отдельными
строками, включая задачи, которые ещё не запущены. При отключённом ревью указано
«Без ревью»; отсутствующее назначение обозначено «Не назначен». Полные имена доступны
в подсказке при наведении. Эти назначения передаются мостом в `Task.queueAssignment`
через snapshot и task.upsert; текущий `assignee` не меняется ради отображения.
Старый мост без этого поля показывает прежнюю строку исполнителя. Для новых подписей
нужно обновить и мод, и мост. Полное описание задачи открывается с начала текста.

Состав настраивается в **Пульт → Команда**: список с перелистыванием, «Добавить агента»
и отдельный список архива. Выбери имя, Codex (приложение или CLI) / Claude Code и роли,
затем сохрани профиль. Новый агент выключен до явного включения. Во вкладке
«Подключение» открой настройку, заполни поля по страницам, сохрани и нажми «Проверить».
Проверка доступна и выключенному агенту. После проверки включи его в редакторе.
Для Codex Desktop нужны ID отдельного чата и `pipePath`; можно импортировать уже
имеющееся подключение. Для CLI нужны каталог проекта, путь к нативному исполняемому
файлу, отдельный UUID подключения и права (`workspace-write` для разработки).
Для Claude нужно заранее подготовленное рабочее пространство с `access.json` и
`conversation.json`; в редакторе укажи его путь и `sessionId` из этого файла.
Редактор не создаёт аккаунты, рабочие пространства Claude или чаты Codex.

Доступные роли приходят из моста. Codex поддерживает все три роли; для создания
черновиков планировщику дополнительно выдаётся разрешение `draft grant` (см. ниже).
Claude также поддерживает все три роли, включая planner+reviewer. Разрешение на
черновик привязывается к его agentId, сессии и проектам из access.json. Планирование
не выдаёт права согласования, запуска или назначения исполнителей.

«Проверить» не вызывает модель, не запускает задачу и не редактирует проект:
Desktop читает выбранный чат, CLI проверяет версию/команды/вход, Claude — своё
рабочее пространство, сессию и `auth status`. Наличие настроек авторизации SDK
Claude показывается отдельно и не выдаётся за проверенный доступ к API. На время
проверки смена или включение этого агента блокируются. Ошибка оставляет введённые
поля на экране. При конфликте версии перечитай настройки перед повтором.

В «Действиях» открываются внешность (включая свой PNG), характер и фразы, личные
места и видимость. Настройщик мест выбирает любого агента текущей команды.
Архив скрывает и выключает персонажа, сохраняя ID, подключение, память, историю и
места. Восстановление возвращает тот же ID, но оставляет исполнителя выключенным:
проверь его подключение и включи явно. Занятого агента или исполнителя незавершённой
задачи сначала нужно остановить и освободить от назначений.

У старой перенесённой пары редактор состава остаётся прежним до явного `queue.enable`;
новый экран доступен в профиле с ролевой очередью. Личные установка и мост не меняются
от сборки исходников.

В пульте и на столе планирования открой «План» → «Новая задача». После описания
выбери проект, разработчика и ревьюера. У агентов должны быть соответствующие роли.
Одного агента нельзя назначить на обе роли. Имена, провайдеры и скины не определяют
назначение: очередь хранит постоянные ID агентов.
ID всех участников разработки сохраняются по попыткам. Ни один из них не может
проверять эту же задачу после смены назначения или перезапуска моста.

В «Настройках» включается «Мост выбирает агентов сам». Для незаполненного назначения
выбирается первый свободный включённый агент с нужной ролью в порядке команды.
Подключение должно поддерживать проект и операцию. Назначения закрепляются перед
разработкой; замечания ревью возвращаются тому же разработчику. Недоступный ревьюер
не заменяется молча другим и не означает разрешения пропустить проверку.

«Без ревью» — явное свойство отдельной задачи. Такой пункт завершается после
успешного отчёта разработчика. Без доступного исполнителя карточка остаётся в очереди
с причиной. Назначения ещё не запущенного пункта меняются кнопкой «Исполнители».
В выборе исполнителей нет выключенных или архивных агентов. Пустое назначение
подписано «Не выбран» при ручном выборе и «Автоматически» при включённом автовыборе.
Сохранение ждёт подтверждения моста; ошибка оставляет карточку назначения открытой.
Без активной попытки той же кнопкой можно заменить ревьюера при ожидании ревью,
между раундами исправлений и в стадии вопроса. Проект, диапазоны и необходимость
проверки сохраняются. Вопрос меняет владельца только при замене исполнителя своей
фазы; замена ревьюера во время вопроса разработчика не закрывает этот вопрос.

Между попытками разработки (очередь исправлений или вопрос разработчика без попытки)
можно выбрать другого разработчика и нажать **«Подтвердить смену разработчика»**.
Мост проверяет окончание работы прежнего исполнителя, чистый Git и совпадение HEAD
с последним сохранённым диапазоном. Новый разработчик продолжает в том же каталоге;
блокировка, история диапазонов и все прежние авторы сохраняются. Ни один из авторов
не может стать ревьюером этой задачи. Замена не разрешает пропустить проверку.
Вопрос после переназначения нужно разрешить отдельно. Если старая попытка ещё закреплена
за агентом, сначала останови её и выполни повтор с ответом после проверки Git.

После сохранения план нужно согласовать кнопкой «В очередь» и запустить на вкладке
«Очередь». Одна очередь обслуживает все подключённые проекты. Исполнение идёт
последовательно; зависимости должны завершиться. При равном приоритете сохраняется
порядок добавления. Состояния: план, в очереди, разработка, ревью, вопрос, готово, отменено.

## Результаты и блокировка проекта

Каждая попытка получает уникальный `run`, ID исполнителя, фазу и отпечаток подключения.
Для завершения разработки нужны новый коммит, чистая рабочая копия (включая
неотслеживаемые файлы), `ci: pass` и описание фактически выполненных проверок.
Ревью проверяет точные диапазоны коммитов всех попыток и конкретный HEAD. При изменении
HEAD или грязной рабочей копии заключение не принимается. Обычный ответ, отсутствие
сообщений или таймаут не означают успех.

Отчёт можно передать финальным JSON-ответом в том же разговоре либо через локальный
`studio.mjs`. Повтор идентичного отчёта разработчика идемпотентен. Ключ ревью
одноразовый: даже идентичный повтор принятого вердикта отклоняется. Чужой агент, другая
фаза, прежний запуск, изменённое подключение или другой результат для того же запуска
отклоняются. Локальный интерфейс наследует доверие моста к процессам текущего компьютера;
ID в JSON не является отдельной криптографической авторизацией.

Результат `changes` возвращает задачу назначенному разработчику. После второго раунда
с замечаниями нужен ответ пользователя. `question`/`blocked` создают вопрос на доске.
Он блокирует эту работу и её каталог, но позволяет очереди обслуживать другой проект
с другим свободным исполнителем после завершения текущего процесса. Путь каталога
сравнивается после разрешения ссылок; два названия одного каталога не обходят блокировку.
Пока за агентом закреплена нерешённая попытка, он не получает другую задачу даже при
простаивающем подключении. На ожидающей карточке указана задача, удерживающая агента;
автовыбор пропускает его. Это действует для вопроса, `blocked`, остановки разработчика
и завершения ответа без отчёта.

Управление и подсказка проекта сначала выбирают активную попытку агента. Если в состоянии
старого моста уже оказались две попытки одного агента, повтор или отмена старого вопроса
отклоняется до остановки процесса, пока активна другая задача. Сначала заверши активную
работу, затем разреши старый вопрос; он не прерывает текущую работу в другом проекте.

Отчёт может поступить до выхода процесса. Следующий этап ждёт его подтверждённого
завершения. При повторе или отмене попытки сначала подтверждается реальная остановка,
затем проверяется чистота Git. Если остались изменения, их надо проверить и сохранить
или убрать вручную: мост не сбрасывает файлы. Внешние ручные изменения не исключаются
блокировкой очереди и проверяются через Git.
Если после принятого результата появился ещё коммит или несохранённые изменения,
карточка объясняет причину оставшейся блокировки и показывает «Освободить проект».
Кнопка работает после завершения процесса и проверки чистоты Git. Она не подменяет
принятый коммит задачи текущим HEAD. При грязном каталоге сначала проверь и сохрани изменения.

## Управление и перезапуск

«Пауза», «Стоп» и «Планирование» в общей очереди прекращают выдачу новых работ.
Карточка агента отдельно управляет его реальным запуском: пауза/стоп отображаются
после подтверждения транспорта, продолжение возобновляет его разговор. Другие агенты
от этого не останавливаются. Остановка задачи требует последующего решения на доске.

Разработчику можно написать, пока его проект занят. Карточка показывает подсказку
«Проект занят задачей tN». Собственные ограничения транспорта сохраняются: занятый
Claude/CLI не получает второй процесс той же сессии. Сообщение не создаёт новую задачу.

После перезапуска очередь на паузе. Незаконченные попытки становятся вопросами;
«Начать» не отправляет их повторно. Проверь разговор и Git, затем ответь на вопрос
или выбери «Повторить» с пояснением проверки прежнего запуска. Старый `run` недействителен.
Пустой ответ отклоняется, исходный вопрос остаётся открытым.

При вопросе ревью «Повторить» предлагает два пути: восстановить проверяемый HEAD
вручную и повторить ревью либо явно вернуть работу разработчику. Во втором случае
добавленные коммиты включаются отдельным диапазоном; разработчик проверяет их и
готовит новую попытку. Следующее ревью получает все диапазоны. Новая история должна
продолжать проверяемый коммит: при разошедшихся ветках сначала разберись с Git вручную.
Выбор обычного повтора при другом HEAD возвращает пояснение, не создавая цикл запусков.

## Подключения и полномочия

- Codex Desktop использует назначенный локальный чат и его настройки доступа.
- Codex CLI работает в каталоге своего подключения; для разработки требуется
  `workspace-write`, для ревью подходит `read-only`. Стандартный workspace-write
  защищает `.git` от записи: файлы и тесты работают, но для автоматического
  коммита нужно отдельное разрешение на Git-запись. Текущий экран подключения
  его не настраивает. Цикл Codex CLI-разработчик → Claude-ревьюер прошёл живую
  приёмку в отдельном проекте с явно разрешённой записью в его `.git` и CLI
  0.163.0-alpha.2. Обратная пара также прошла в установленном тестовом пакете:
  Claude SDK создал коммит, Codex CLI в read-only независимо проверил его и тесты.
  Подробности — в [PORTABLE_TRIAL.md](PORTABLE_TRIAL.md).
- При паузе и остановке Codex CLI мост проверяет дерево процессов до и после
  завершения родителя. Оставшиеся дочерние процессы проверяются по PID и времени
  создания; повторно использованный PID не считается прежним процессом агента.
  Подтверждение ждёт завершения дерева и закрытия каналов вывода (до 30 секунд).
  Если таблица процессов недоступна или время создания неизвестно, мост сообщает
  об ошибке и сохраняет возможность повторить «Стоп», не объявляя остановку успешной.
- Claude-разработчик использует Claude Agent SDK прямо в каталоге проекта, без
  worktree и без переключения моста в `claude-backend`. Нужны установленный Claude
  Code и проект в `access.json` пространства этого агента. Авторизация SDK подчиняется
  общей политике `agents/claude/auth.ts`: по умолчанию требуется `ANTHROPIC_API_KEY`,
  настроенный облачный провайдер (`CLAUDE_CODE_USE_BEDROCK`, `_VERTEX`, `_FOUNDRY`,
  `_ANTHROPIC_AWS`) либо API-шлюз (`ANTHROPIC_AUTH_TOKEN` вместе с `ANTHROPIC_BASE_URL`).
  Без них SDK не вызывается и файл сессии разработки не создаётся; ошибка становится
  вопросом задачи. `CLAUDE_CODE_OAUTH_TOKEN` удаляется из окружения API-запуска.
  Вход claude.ai допускается только при явном личном opt-in оператора:
  `--use-claude-login`, `AGENTCRAFT_USE_CLAUDE_LOGIN=1` или
  `config.json` → `claude.useClaudeLogin: true`. Выбор роли developer и наличие
  входа Claude Code сами по себе не включают этот режим. В переносимом пакете
  исключения нет. SDK получает `CLAUDE_AGENT_SDK_CLIENT_APP=agentcraft-foreman/<version>`.
  Для каждой попытки создаётся отдельная SDK-сессия; пауза/продолжение сохраняют её,
  новый run создаёт новую. ID хранится в `agents/<id>/claude-developer.json` профиля.
  Диалог и ревью продолжают использовать общий разговор и его инструменты MCP;
  разработка не смешивается с историей этого разговора.
  Агент сохраняет одно текущее владение: пока его общий разговор открыт в терминале
  или Code, новая SDK-разработка не стартует. Верни разговор в игру; проверка
  повторяется непосредственно перед отправкой, а не только во время опроса.
- SDK-разработчику доступны `Read, Write, Edit, Glob, Grep, Bash, TodoWrite`.
  Общая с прежним Claude backend политика `policy.ts` проверяет вызовы через
  `PreToolUse` и `canUseTool`: безопасные операции внутри проекта разрешены,
  внешние пути, сеть и неизвестные команды требуют игрового решения, push запрещён.
  Полная команда и каталог видны в вопросе о разрешении. Изменённый доступ к проекту
  перепроверяется перед инструментами. Настройки пользователя/проекта не загружаются
  как настройки CLI (`settingSources: []`); AGENTS.md остаётся инструкцией разработчику.
- Отчёт SDK имеет строгую JSON-схему с task ID, agent ID и UUID попытки.
  Перед передачей финального результата runtime проверяет завершение дерева процессов.
  Пауза и стоп также ждут проверки CLI и потомков. Если таблица процессов недоступна
  или процесс жив, остановка не подтверждается: повтори «Стоп». Сохранённая запись
  `.process.json` удерживает агента занятым и после перезапуска моста до проверки.
  Пауза сохраняет запрос, стоп удаляет его; ни одно действие не запускает следующую
  задачу само по себе.
  При остановке и закрытии адаптера мост независимо пытается остановить оба
  исполнителя (SDK и диалог). Ошибка одного не пропускает остановку другого и не
  считается подтверждённым завершением. Если остановка не подтверждена, мост
  возвращает ошибку, не ожидая бесконечно незавершённого ответа.

Разработчик получает команду не делать push/deploy. Разрешённый shell разработчика
и режим Codex Desktop не являются файловой песочницей одного каталога. Проверка Git
защищает принятие результата ревью, но не является системным запретом записи у Codex
с более широкими правами. Не следует выдавать такое подключение за read-only.

## Перенесённая пара A4

Профили без `team.json` продолжают использовать прежнюю очередь. Перенесённая пара
сохраняет прежний режим до явной команды `queue.enable` или кнопки «Перейти на очередь
с ролями» в настройках. Сначала заверши текущую работу/диалог, разреши вопросы старой
очереди и сними личные паузы. Переход переносит карточки и назначения marlow/wren,
сохраняет старую запись `backend.studio` и курсор Codex, не создаёт новые разговоры.
Новая очередь запускается на паузе. Имена, память, места и внешность остаются в профиле.
Это действие не выполняется автоматически при установке или сборке.

## Локальный интерфейс

Все действия: `node tools/studio.mjs <action> --file <json> --port <port>`
(в переносимом пакете файл находится в корне). `get` возвращает очередь и команду.

```json
{"title":"Исправление","description":"Описание","expected":"Результат","repoId":"project-id","developerId":"agent_id","reviewerId":"other_id","noReview":false,"deps":[],"priority":0}
```

- `create`, `edit` — данные выше; `edit` дополнительно требует `id` и стадию «план».
- `approve`: `{ "id": "t1" }`.
- `assign`: `{ "id": "t1", "developerId": "agent_id", "reviewerId": null, "noReview": false }`.
  `null` означает автоматический выбор, если настройка включена. Уже начатую попытку
  переназначать нельзя. В ожидающем ревью, очереди исправлений и вопросе без активной
  попытки допустим `{ "id": "t1", "reviewerId": "replacement_id" }`.
  Для замены разработчика между его попытками требуется конкретный ID и
  `confirmDeveloperChange: true`: `{ "id": "t1", "developerId": "new_id", "confirmDeveloperChange": true }`.
  Проект и `noReview` уже начатой задачи изменить нельзя. Поля, не переданные в `assign`,
  сохраняются. `canAssignReviewer`/`canAssignDeveloper` в `get` управляют доступностью
  редактора; сервер повторно проверяет ограничения при сохранении.
- `settings`: `{ "revision": 3, "autoSelect": true }`; ревизия берётся из `team.get`.
- `start`, `pause`, `stop`, `plan`: пустой объект.
- `retry`: `{ "id": "t1", "answer": "Проверил прежний запуск; ответ…" }`.
  Для вопроса ревью необязательное `recovery` выбирает `restore-head` (по умолчанию)
  либо `developer` (вернуть разработчику и включить добавленные коммиты в ревью).
- `cancel`, `release`, `prioritize`: `{ "id": "t1" }`. `release` освобождает каталог
  завершённой карточки после проверки исполнителя и чистоты Git.
- `connection.control`: `{ "id": "agent_id", "control": "pause" }` (или resume/stop).

Разработчик, действие `report`:

```json
{"id":"t1","run":"UUID попытки","agentId":"agent_id","status":"done","summary":"Результат","checks":"Выполненные проверки","ci":"pass"}
```

Ревьюер, команда `node tools/studio.mjs review --file <JSON-файл вне проекта> --port <port>`.
Вызов `review.report` также поддерживается. Оба имени используют одну проверку ключа
и схемы, а повтор принятого вердикта завершает CLI с ненулевым кодом:

```json
{"id":"t1","run":"UUID попытки ревью","agentId":"other_id","head":"полный SHA","verdict":"pass","summary":"Заключение"}
```

Вердикты: `pass`, `changes`, `question`. Для разработчика доступны `done`, `question`,
`blocked`. Пул можно создать вручную в пульте или дать Codex-планировщику
ограниченное разрешение на черновик, описанное ниже.

## Claude как планировщик новой команды (t52)

Выбери включённого Claude с ролью `planner` (можно одновременно `reviewer`) и его
собственным подключённым разговором. Рабочее пространство и `sessionId` должны
совпадать с подключением. Открой режим планирования без незавершённых попыток.
Оператор выдаёт то же разрешение `draft grant`, что описано ниже, но записывает
`--out` в **planning.json выбранного рабочего пространства Claude**. Для установленного
пакета команда находится в `studio.mjs`, для исходников — в `tools/studio.mjs`.
Существующий файл не перезаписывается: оператор сначала сохраняет его под другим именем.
Не копируй старый legacy planning.json: новая очередь использует формат версии 2.

Каждое разрешение действует 30 минут и позволяет создать одну карточку. Оно привязано
к agentId и отпечатку подключения, включая workspace/sessionId. Следующая карточка
требует нового разрешения. Для Claude можно разрешить только проекты из его access.json;
пути и текущий доступ перепроверяются при каждом запросе. `planning_list` возвращает
карточки только разрешённых проектов, а `workspaceProject` связывает ID проекта доски
с его ID в инструментах чтения исходников. Зависимости тоже ограничены этими проектами.

После выдачи разрешения напиши выбранному агенту через его карточку просьбу создать
обсуждённый черновик. `planning_list`/`planning_create` работают через ограниченный
канал `/planner`: без общей памяти других агентов, управления командой или очередью.
История, инструкции и MEMORY.md остаются в отдельном пространстве/сессии агента.
Повтор того же requestId/содержимого возвращает прежний ID, в том числе после перезапуска.
Смена сессии, подключения или роли отменяет действие старого разрешения.

Черновик остаётся в стадии «План». Пользователь отдельно назначает исполнителей,
согласует и запускает работу. Автор плана может проверять чужую разработку; собственную
разработку и работу любого прежнего автора этой задачи проверять по-прежнему запрещено.
Старые парные профили продолжают использовать прежний planning.json версии 1.
Новый исходный код не обновляет автоматически установленный релиз 0.4.13-rc.1.

## Codex как планировщик (A14)

Работает в новой ролевой очереди с включённым Codex-агентом, имеющим роль `planner`
и подключение Desktop либо CLI. Старая парная очередь сохраняет отдельные инструменты
Claude `planning_list`/`planning_create`; команда ниже её не переводит автоматически.
Открой режим планирования и заверши активные/неразрешённые попытки задач.

Оператор выбирает ID агента из `team.get` и ID уже добавленных проектов из `get`,
сохраняет запрос разрешения вне репозитория:

```json
{"agentId":"agent_id","projects":["repo-id"]}
```

Затем выдаёт одноразовое разрешение; `--out` должен указывать **новый** приватный
файл. Токен не печатается в консоль и не попадает в общие снимки состояния:

```powershell
node tools/studio.mjs draft grant --port 7878 --file <grant.json> --out <permit.json>
```

Передай планировщику путь к `permit.json` и просьбу составить черновик. Агент вызывает:

```powershell
node tools/studio.mjs draft list --permit <permit.json>
node tools/studio.mjs draft create --permit <permit.json> --file <draft.json>
```

Формат `draft.json`:

```json
{"requestId":"plan-item-1","project":"repo-id","title":"Название","description":"Что сделать","expected":"Проверяемый результат","deps":[],"priority":50}
```

`project` выбирается из `projects` ответа `list`; зависимости — ID карточек этого
пула. Список возвращает по две полные карточки с `total`/`nextOffset`. Для следующей
страницы передай `--file <page.json>` с `{"offset":2}`. Ожидаемый результат обязателен;
разработчик, ревьюер и отключение ревью не задаются планировщиком.

Разрешение действует 30 минут и позволяет создать **одну** карточку. Для следующей
карточки оператор выдаёт новый файл. Повтор `create` с тем же `requestId` и содержимым
возвращает `duplicate:true` и прежний ID; другой текст с тем же ключом отклоняется.
Ключи разделены по агентам. После истечения токена оператор может выдать новый для
повтора: сохранённый `requestId` всё равно не создаст дубликат. Ошибки входных данных
не расходуют разрешение. Карточка, её ключ и использованный токен сохраняются одной
записью состояния; сервер хранит только хеш токена.

Каждый запрос повторно проверяет режим, отсутствие активных попыток, включённого
агента и роль `planner`, неизменность подключения и каталогов разрешённых проектов.
После перезапуска мост ставит очередь на паузу; пользователь сначала возвращает
планирование. Черновик остаётся несогласованным, не получает исполнителей и не
запускает модель. Согласование, назначения и запуск выполняет пользователь в пульте.

Helper отправляет запросы по ограниченному WebSocket-пути `/planner`. Он принимает
только `draft.list`/`draft.create`, требует токен при каждом запросе, не передаёт
историю разговоров и общие обновления. Повторный `hello` не снимает ограничения.
С тем же токеном нельзя выдать новый токен, согласовать, запустить, изменить или
отменить карточку. CLI с `--permit` также отклоняет остальные команды. Основной
локальный канал управления остаётся доверенным каналом оператора и игры: эта
проверка возможностей не изолирует процесс, уже имеющий полные права пользователя
на машине. Не публикуй `permit.json`; удали его после использования.

## Codex как ревьюер

Назначь Claude разработчиком, а отдельного Codex-агента — ревьюером. Подходят
Codex Desktop и Codex CLI; для CLI каталог подключения должен совпадать с проектом.
Запрос содержит задачу, ожидаемый результат, проверки разработчика, все диапазоны
коммитов и HEAD. Codex получает явный запрет изменять файлы и выполнять команды,
меняющие проект. Вердикт возвращается финальным JSON в назначенный разговор либо
командой `review` выше. `pass` завершает пункт, `changes` возвращает его разработчику,
`question` открывает вопрос пользователю. Лимит раундов исправлений сохраняется.

Перед отправкой запроса и при получении вердикта мост проверяет `cleanHead`: рабочая
копия должна быть чистой, HEAD — совпадать с зафиксированным результатом разработчика.
Изменённые, подготовленные к коммиту и новые неотслеживаемые файлы также отклоняют
заключение и создают вопрос на доске. Мост не исправляет и не удаляет эти файлы.
После паузы отчёт не принимается до продолжения; после остановки прежний ключ
недействителен, повторное ревью получает новый UUID. Изменение подключения тоже
отклоняет результат. Вердикт требует строго `pass`, `changes` или `question` и
непустой `summary`; лишние поля отклоняются.

Это проверка результата, а не технический запрет записи: права принадлежат
подключению Codex. Для CLI выбирай `read-only`, если требуется ограничить запись
на уровне его песочницы. Desktop использует права выбранного чата. Проверка Git
не обнаруживает временную правку, полностью отменённую до отчёта, и не защищает
игнорируемые или внешние файлы. Не выдавай её за изоляцию файловой системы.

## Проверка

`foreman/test/role-queue.test.ts` проверяет назначения, диапазоны, блокировки, отчёты,
подтверждение управления и восстановление. `agent-runtime.test.ts` проверяет путь
через адаптеры и обработку финального JSON. Проверки используют временные Git-проекты
и управляемые транспорты, без вызова моделей и без личного профиля. Сборка Gradle
проверяет клиентский код; визуальная проверка в запущенном Minecraft и настоящие
модельные задания остаются отдельными проверками.

`claude-developer.test.ts` проверяет SDK-конфигурацию, разрешения через настоящий
обработчик игровых решений, чужой каталог, UUID отчёта, паузу/продолжение/стоп,
живые процессы и восстановление записей после перезапуска. Ошибка SDK становится
вопросом очереди с сохранением попытки и блокировки проекта; опрос адаптера не
заменяет ошибку статусом паузы.

Проверки авторизации используют имитацию SDK: отказ до запуска без API-аутентификации,
API/облачные провайдеры/шлюз, удаление OAuth-переменной, явный opt-in, повторная проверка
при продолжении и передача настройки из runtime. Также проверяются независимая
остановка обоих исполнителей и запрет запуска при переносе разговора в Code после опроса.

Отдельный платный/лимитируемый прогон требует установленного Claude Code и настроенной
API-аутентификации/облачного провайдера в окружении. Тестовый профиль использует режим
API по умолчанию; наличие входа Claude Code не заменяет эту настройку:

```powershell
cd foreman
$env:AGENTCRAFT_TEST_REAL_CLAUDE = '1'
node node_modules/vitest/vitest.mjs run test/claude-developer.test.ts -t 'LIVE:'
Remove-Item Env:AGENTCRAFT_TEST_REAL_CLAUDE
```

Этот прогон создаёт временный профиль и Git-проект, вызывает настоящего Claude SDK,
проверяет файл, тест, коммит, принятие отчёта runtime и передачу диапазона другому
агенту. Транспорт ревьюера имитируется; настоящего модельного ревью он не проверяет.
Без переменной окружения прогон пропускается и модели не вызываются. Рабочий цикл
разработки проходил живую проверку 2026-10-08 на Windows до исправления режима
авторизации; новый платный прогон с API-аутентификацией не выполнялся. Личный мост
и Minecraft не перезапускались; визуальная проверка разрешений в игре отдельно
не выполнялась.

`codex-review.test.ts` проверяет оба адаптера, три вердикта, ошибки исполнителя,
остановку и команду `studio.mjs review` через настоящий временный WebSocket-мост.
Код разработки в этом наборе — имитация результата Claude, а IPC Desktop и процесс
модельного ответа CLI заменены управляемыми транспортами. Модель Codex, чужие чаты
и личный мост не вызываются. Настоящее модельное ревью Codex и визуальная проверка
в Minecraft для A7 не выполнялись; эти тесты не заявляют обратного.

Отдельная живая приёмка установленного пакета 2026-10-09 проверила настоящую
пару Claude SDK-разработчик → Codex CLI-ревьюер. Для личного теста пользователь
явно разрешил вход Claude Code; opt-in передан только процессу тестового моста.
Claude создал коммит d4db416, Codex в read-only проверил точный диапазон и сам
запустил 7 успешных тестов; очередь приняла pass и завершила t4. Это не прогон
с API-аутентификацией и не проверка Codex Desktop или игровых разрешений.
Свидетельства и ограничения: [PORTABLE_TRIAL.md](PORTABLE_TRIAL.md).

`codex-planning.test.ts` проверяет настоящий CLI и временный WebSocket-сервер:
одноразовое разрешение, роли и подключения, разрешённые проекты, зависимости,
страницы списка, повторные/одновременные запросы, сохранение после перезапуска,
запрет управляющих команд и сохранение пользовательского согласования.
Модельные ответы заменены управляемым адаптером; личный мост не используется.
