# Модель настраиваемой команды AgentCraft

Статус: спецификация A1 / t36 согласована запуском пользователем задачи A2 / t38. Это целевой контракт; реализованный объём A2, подключения A3, клиентский состав A8 и ограничения описаны в [CODEX_OBSERVER.md](CODEX_OBSERVER.md#per-agent-connections-a3--t39). Последующие этапы и установка не считаются завершёнными.

Основание проверки текущего поведения: исходники на коммите `924a9db`. Текущая система описана в [CODEX_OBSERVER.md](CODEX_OBSERVER.md), действующий протокол — в [protocol.md](protocol.md). При реализации соответствующего этапа эти документы нужно обновить вместе с кодом.

## 1. Цель и границы

Пользователь устанавливает мод с локальным мостом, подключает собственные проекты и создаёт произвольное число агентов Codex и Claude. Провайдер, набор рабочих ролей, личность и внешний вид независимы. Можно иметь двух Codex, двух Claude или смешанную команду. Нет обязательного состава из шести персонажей и ограничения команды двумя агентами. Практические ограничения ресурсов должны сообщаться явно, а не обрезать состав команды.

Роли: `planner` — планировщик, `developer` — разработчик, `reviewer` — ревьюер. Агент может иметь несколько ролей. Наш целевой состав: Codex-разработчик и Клава-планировщик/ревьюер. Роль разрешает действие только при наличии реально работающего подключения с соответствующей возможностью; она сама по себе не выдаёт инструменты и доступ к файлам.

Первый этап использует одну последовательную очередь на весь профиль моста, включая все его проекты. Параллельное выполнение задач, облачная оркестрация, автоматические push/deploy и перенос авторизации между пользователями сюда не входят. Подключения используют авторизацию владельца установки. Общение, утверждение плана и разрешение на публикацию — разные действия.

## 2. Источники данных и формат `team.json`

`<profile>/team.json` — единственный источник состава команды и её настроек. Состояние выполнения, задачи, история, сессии и игровые координаты остаются отдельными данными. Мод получает проекцию состава через мост; встроенный каталог скинов не создаёт агентов.

Предлагаемый формат версии 1, пример перенесённой команды:

```json
{
  "version": 1,
  "revision": 1,
  "assignment": { "autoSelect": false },
  "agents": [
    {
      "id": "marlow",
      "name": "Codex",
      "provider": "codex",
      "roles": ["developer"],
      "enabled": true,
      "visible": true,
      "archived": false,
      "appearance": { "skin": "marlow", "color": "#858ED1", "slim": false },
      "personaRef": "agents/marlow/persona.json",
      "connectionRef": "connections/marlow.json",
      "memoryDir": "agents/marlow/memory",
      "instructionsDir": "agents/marlow/instructions"
    },
    {
      "id": "wren",
      "name": "Клава",
      "provider": "claude",
      "roles": ["planner", "reviewer"],
      "enabled": true,
      "visible": true,
      "archived": false,
      "appearance": { "skin": "wren", "color": "#D78E65", "slim": false },
      "personaRef": "agents/wren/persona.json",
      "connectionRef": "connections/wren.json",
      "memoryDir": "agents/wren/memory",
      "instructionsDir": "agents/wren/instructions"
    }
  ]
}
```

Это пример структуры, не предписание заменить реальные имена, флаги или внешность нашей команды значениями из примера.

| Поле | Контракт |
| --- | --- |
| `version` | Версия схемы файла. Неизвестная версия не перезаписывается и не заменяется стандартной командой. |
| `revision` | Целая возрастающая ревизия. Изменение из пульта содержит ожидаемую ревизию; конфликт возвращает ошибку с сохранением черновика. |
| `assignment.autoSelect` | Настройка «Мост выбирает сам», по умолчанию `false`. Не разрешает запуск несогласованных задач. |
| `id` | Неизменяемый уникальный ключ, `[a-z0-9_-]{1,64}`. Новый ключ генерируется независимо от имени и провайдера. Не переиспользуется после архивации. Старые `marlow`/`wren` допустимы как обычные ключи. |
| `name` | Отображаемое имя, 1–28 символов после удаления крайних пробелов, длина в UTF-16 для согласованности Java/JS. При совпадении имён выбор показывает также id. |
| `provider` | Строго `codex` или `claude`. Не выводится из id, имени, скина или позиции в массиве. |
| `roles` | Непустой набор уникальных значений `planner`, `developer`, `reviewer`. Порядок не задаёт старшинство. |
| `enabled` | Разрешает агенту принимать работу и сообщения через мост; не равнозначен видимости. Выключение занятого агента требует подтверждённой остановки или завершения его работы. |
| `visible` | Показывает персонажа в мире. Скрытие не отключает исполнителя и не убирает его из команды/истории. |
| `archived` | Исключает агента из действующей команды, адресатов и назначения новых задач, сохраняя данные. Архивный агент имеет `enabled=false`, `visible=false`. |
| `appearance` | Ссылка на скин, цвет `#RRGGBB`, модель рук. Прочие существующие настройки внешности сохраняются при переносе; серверная модель и локальные настройки должны иметь явное распределение ответственности. |
| `personaRef` | Отдельный файл личности: описание и фразы по событиям. Не содержит полномочия. Текущие ограничения редактора фраз сохраняются; его схема обобщается на любой id. |
| `connectionRef` | Ссылка на отдельную конфигурацию подключения. У нового неподключённого агента допустим `null`; в пульте показано «Не подключён». |
| `memoryDir`, `instructionsDir` | Папки личной памяти и инструкций. Общие правила проекта подключаются отдельно и не превращают личную память в общую. |

Все поля примера обязательны, кроме допускаемого `null` у `connectionRef`; неизвестные поля версии 1 отклоняются. Относительные пути разрешаются от корня профиля, нормализуются и проверяются с учётом ссылок/junction; выход за пределы профиля не допускается. Разрешённые внешние проекты и прежняя папка Claude задаются отдельной проверяемой конфигурацией доступа/подключения, а не обходом этих ограничений. Повреждённый файл вызывает понятную ошибку; мост не создаёт вместо него стандартных персонажей.

Запись атомарная, через общую блокировку изменения команды; перед переносом схемы создаётся резервная копия. При удалении, смене роли или подключения проверяются активные запуски и назначения. Нельзя принимать старый ответ после такой смены как результат нового запуска.

## 3. Подключения, сессии, память и полномочия

Конфигурация подключения содержит собственный id, `provider`, тип транспорта (`codex-desktop`, `codex-cli`, `claude-code`) и локальные параметры. Секреты авторизации не помещаются в `team.json`, игровые снимки, логи или распространяемый пакет. У двух агентов одного провайдера могут быть один аккаунт и одинаковая модель, но должны быть разные привязки разговоров и состояния выполнения.

- **Codex Desktop:** отдельный файл привязки и курсор чтения на каждого агента. Не использовать общий `~/.agentcraft/codex-chat.json` как единственную привязку команды. Сохранять проверку идентичности чата и подтверждение управления его реальным выполнением.
- **Codex CLI:** отдельный адаптер запуска, продолжения, чтения результата и остановки процесса с собственной сессией каждого агента. Это требование к реализации, не уже существующий путь подключения. До объявления транспорта готовым проверить интерфейс установленной CLI и поддержку всех необходимых действий; команды и флаги здесь не выдумываются. Один разговор между Desktop и CLI автоматически не обещается.
- **Claude Code:** отдельное рабочее пространство/указатель на него, идентификатор разговора, курсор и блокировка владения на каждого агента. Продолжение в игре, терминале и разделе Code сохраняет разговор конкретного агента. Одновременно им владеет только один исполнитель; блокировка одного агента не блокирует разговоры остальных.
- **Планирование и MCP:** привязка планирования настраивается отдельно для каждого агента-планировщика и связывает его id, профиль моста, рабочее пространство и разрешённые проекты. Единственные `planning.json`/`claude-workspace.json` профиля заменяются адресуемыми привязками; второй планировщик не перезаписывает первого и не использует его полномочия. Разрешения MCP формируются для конкретного агента и операции. Имя MCP-сервера и соответствующие имена разрешённых инструментов согласуются в конфигурации запуска, `.mcp.json` и `.claude/settings.json`, а не выводятся из имени персонажа. Текущие `klava` и `mcp__klava__planning_list/create` — совместимость существующего подключения, не универсальная привязка всей команды. Право создавать черновики не даёт права запускать очередь или утверждать план. Смена роли требует согласованного обновления разрешений в игре, терминале и Code; перезапуск не должен возвращать прежние более широкие права.
- **Ярлыки и локальные инструкции Claude:** настройка общего разговора и запускатели должны выбирать конкретного агента/его workspace и сессию. Создаваемые `CLAUDE.local.md`, история и ярлыки запуска, продолжения, открытия Code и возврата в игру не могут оставаться общей конфигурацией одной Клавы для всех агентов. Пользовательские инструкции сохраняются, персональные названия генерируются из настроек агента; права разработчика не выдаются путём отключения ограничений у всех ревьюеров.
- Нельзя привязать одну и ту же сессию к двум агентам. При обнаружении дубликата подключение отклоняется с указанием конфликта. Аккаунт не считается идентификатором сессии.
- История диалога и история технических запусков различаются: запуски задач/ревью могут иметь отдельный технический контекст, но их результаты адресуются владельцу агента и его журналу. Существующий `ClaudeReviewer` не сохраняет нативную сессию ревью; единый разговор не означает, что такая история уже доступна в терминале.
- Личность применяется к репликам игроку. Код, комментарии, коммиты, документы, release notes, отчёты и `verdict/summary` нейтральны. Ролевая инструкция не отменяет правила проекта и разрешения инструментов.

## 4. Реальные возможности провайдеров и требуемая интеграция

«Есть» в таблице означает наличие указанного пути в текущих исходниках. Это не заявление, что все сочетания уже доступны в пульте или проверены на живых аккаунтах.

| Провайдер / роль | Что есть сейчас | Что нужно для целевой команды |
| --- | --- | --- |
| Codex / разработчик | `agents/observer.ts` отправляет задачу в один Desktop-чат; `studio.mjs report` возвращает результат в очередь с проверкой запуска и чистого коммита. | Адаптер на каждого агента, явное назначение разработчика, изоляция статусов/управления; отдельный CLI-транспорт. |
| Codex / планировщик | Общий транспорт `studio.mjs` умеет передавать действие с JSON; `draft.create`/`draft.list` в Studio существуют, но сейчас авторизация и авторство связаны с рабочим пространством Клавы и `wren`. | Команда черновиков через `studio.mjs draft.create`/`draft.list` с привязкой к агенту-планировщику и проекту. Идемпотентный `requestId`; только черновики, без права утверждать или запускать собственный план. Действующий обход через токен Клавы не считается поддержкой Codex-планировщика. |
| Codex / ревьюер | Общие проверки Git и форма `ReviewResult` есть в `studio-review.ts`; готового Codex-ревьюера в Studio нет. `report` сейчас завершает разработку, а не ревью. | Отдельное действие `studio.mjs review.report` (проектируемое), вердикт `pass/changes/question`, назначенный ревьюер, id задачи/запуска, проверяемый commit и диапазоны. При смене HEAD или изменениях рабочей копии результат отклоняется. |
| Claude / разработчик | `agents/claude/index.ts` содержит SDK-движок выполнения в worktree, сессии, остановку, проверки и `canUseTool`; `policy.ts` ограничивает инструменты. В текущем observer-пульте Claude остаётся ревьюером/собеседником. | Переиспользовать механизм выполнения и политики, но подчинить его единой очереди Studio. Не запускать второй независимый планировщик ClaudeBackend. Выдать инструменты разработчика только в соответствующем запуске; сохранить проверки доступа, запрет push и подтверждение остановки. |
| Claude / планировщик | `claude-planning.ts` и MCP `planning_create`/`planning_list` создают черновики с проверкой проекта и повтора запроса. | Убрать зависимость от имени Клава и одного workspace, проверять роль и доступ конкретного агента. |
| Claude / ревьюер | `ClaudeReviewer` получает diff и возвращает структурированный вердикт; проверяет чистоту/HEAD до и после ревью. Дополнительные инструменты рабочего пространства ограничены. | Выбирать конкретного ревьюера, его пространство и полномочия; сохранять адресность и существующее отклонение устаревших результатов. |

Внутренние `lead`/`worker` существующего ClaudeBackend и протокола не являются новыми рабочими ролями. В `policy.ts` сейчас `lead` не может редактировать, а `worker` работает в своём worktree. Адаптер обязан выбирать политику по **текущей операции**, а не навсегда назначать агенту с несколькими ролями полные права разработчика. Ревью и планирование не получают право менять код только потому, что у того же агента есть роль developer.

Для Codex ограничения зависят также от настроек его среды выполнения: текст «только ревью» не является техническим запретом записи. Мост проверяет неизменность проверяемого кода и не принимает ошибочный результат; не следует объявлять такие проверки полноценной изоляцией процесса. Готовность каждой роли/транспорта подтверждается отдельно. Неподдерживаемая комбинация показана как недоступная с причиной, а не как успешно подключённая.

### Контракт результатов

Каждый запуск связывает `taskId`, уникальный `runId`, `agentId`, фазу, проект и подключение/его ревизию. Отчёт из прошлого запуска, чужого агента или изменённого подключения отклоняется. Дубликат уже принятого отчёта не выполняет переход повторно. Смена имени или скина не меняет владельца запуска.

Разработчик передаёт результат и фактически выполненные проверки; успешное завершение требует проверок и зафиксированных изменений. Ревьюер получает точный commit/диапазоны изменений и возвращает отдельный структурированный вердикт. Перед началом и при принятии ревью проверяются HEAD и чистота отслеживаемых/неотслеживаемых файлов рабочей копии по текущему контракту `cleanHead`. При расхождении — вопрос пользователю и новое ревью после проверки, никогда автоматический `pass`. Финальная реплика модели сама по себе не завершает карточку.

## 5. Назначение и одна общая очередь

У задачи хранить `plannerId` (автор плана), `developerId`, `reviewerId`, `reviewPolicy: required|none`, историю назначений и участников разработки. Проект задаётся явно. Имена участников можно сохранять в исторических снимках, но связи строятся по id.

1. Явное назначение имеет приоритет. Перед каждым запуском проверить, что агент не архивный, включён, имеет нужную роль, доступ к проекту и готовое подключение. Назначенного, но недоступного агента не заменять молча даже при включённом автовыборе.
2. При `autoSelect=false` незаполненное назначение требует выбора пользователя. При `autoSelect=true` мост выбирает только для незаполненного назначения из подходящих свободных агентов; порядок — стабильная сортировка по id. Выбор записывается в задачу до запуска и виден на доске. Если подходящего агента нет, показать причину ожидания.
3. Самопроверка запрещена: ревьюер не может быть разработчиком этой задачи или участником её предыдущих попыток. Два агента одного провайдера допустимы при разных id и сессиях. Планировщик может проверять задачу, если не участвовал в её реализации.
4. По умолчанию ревью обязательно. Если пользователь выбирает `reviewPolicy=none`, карточка явно помечается «Без ревью», включая итог. Отсутствие доступного ревьюера не переключает задачу в этот режим. «Без ревью» не означает «Ревью пройдено» и не отменяет проверки разработчика. Записывать, когда пользователь выбрал это исключение.
5. Планировщик создаёт черновики с ожидаемым результатом, зависимостями и приоритетом. Пользователь утверждает их и отдельно запускает очередь. Циклические/неизвестные зависимости отклоняются. Для A1 требуется отдельное согласование документа перед A2, даже если остальные черновики уже находятся на доске.
6. В каждый момент очередь выполняет не более одной фазы одной задачи: разработку либо ревью. Все провайдеры пользуются этим же диспетчером. Последовательность: `plan → queued → coding → review → done`; при явном «Без ревью» — `coding → done`. При замечаниях — возврат на исправление; сохранить существующий предел двух раундов ревью с последующим вопросом пользователю, не создавать бесконечный цикл.
7. `question` означает ожидание решения, `cancelled` — отмену. Ошибка/blocked-отчёт не считается успехом. Очередь не запускает другую задачу до разрешения вопроса или явного решения пользователя пропустить/отменить текущую. Статус проекта, личная пауза агента и состояние общей очереди отображаются раздельно.
8. После перезапуска моста очередь остаётся на паузе до сверки реальных процессов, сессий, состояния Git и активного запуска. Никаких повторных отправок задачи по одному лишь таймауту или отсутствию статуса.

### Прямые сообщения и управление

Сообщение разработчику разрешено и при занятом проекте. Показать подсказку: «В проекте выполняется задача; сообщение может повлиять на текущую работу». Не блокировать отправку из-за блокировки проекта и не превращать её автоматически в новую задачу/разрешение на второй запуск.

Транспортные ограничения сохраняются: нет связи, агент выключен, одна сессия занята другим владельцем либо реальная остановка ещё не подтверждена — отдельные причины, которые нужно показать. Нельзя считать сообщение доставленным без подтверждения или обойти блокировку запуском второго процесса той же сессии. Подсказка сама по себе не исключает ручные изменения извне очереди; проверки состояния Git и привязки отчётов остаются обязательными.

«Пауза», «Продолжить», «Стоп» в карточке адресуются конкретному агенту и реальному запуску; подтверждение отображается после подтверждения транспорта. Управление очередью находится отдельно. Остановка одного агента не прерывает остальных собеседников. Псевдонимы `@codex`/`@claude` допустимы только при единственном подходящем адресате; при двух одноимённых провайдерах нужен выбор, без отправки первому. Обычный ответ адресуется последнему выбранному/ответившему действующему агенту; архивный адресат требует нового выбора.

## 6. Архив вместо удаления

Кнопка «Удалить агента» архивирует его. Перед архивацией активная работа должна завершиться либо быть явно остановлена с подтверждением. Пока остановка не подтверждена, запись остаётся действующей с заметным состоянием ожидания. Архив не уничтожает задачи, переписку, инструкции, память, личность, подключения и назначенные места.

После архивации агент пропадает из мира и обычного списка адресатов; доступен в разделе «Архив». Незавершённые назначения требуют переназначения, а не автоматической отмены или передачи работы. Завершённые задачи сохраняют авторство и результаты ревью. Места не передаются другим агентам автоматически.

«Восстановить» возвращает тот же id и данные, но оставляет исполнителя выключенным до проверки подключения; пользователь выбирает видимость и включает его. Полное стирание данных — отдельная будущая операция, не часть этой кнопки и не часть A1.

## 7. Места, внешность и поведение в мире

Новый агент использует общие места профиля/мира до ручного назначения. Настройщиком можно выбрать любого действующего агента и назначить его личные места. Приоритет: личное место соответствующего типа → общее место → безопасная позиция ожидания с подсказкой о ненастроенном месте. Отсутствие стола не означает отсутствия реальной работы и не должно создавать фиктивный статус отдыха.

Сохранить существующие типы `desk`, `library`, `testbench`, `terminal`, `mergestation`, `meeting`, `lounge`, `user`, а также существующие настройки вариантов отдыха и танца. Координаты привязаны к миру/измерению и id агента, не хранятся в `team.json`. Новые агенты не требуют перестройки HQ. Общие места распределяются с учётом занятости физических позиций; персонажи не получают автоматически один и тот же стул.

Роль определяет доступные действия, текущая фаза — игровое поведение: планирование у `meeting`, разработка у `desk`, проверки у `testbench`, ревью у `mergestation`, запрос решения у `user`. Когда точное действие неизвестно, показывать реальную общую активность, не придумывать чтение или запуск тестов. Режим обсуждения плана направляет участвующих планировщиков к общему/личному месту планирования. Существующие анимации переиспользуются; новая анимация для каждой роли не требуется.

Скин выбирается из каталога независимо от id. Файлы старых скинов можно сохранить без появления их владельцев в команде. Восстановление из архива возвращает прежние места; пропавшее/недоступное место требует переназначения.

## 8. Согласованная версия протокола

Сейчас TypeScript и Java используют версию wire-протокола 1. Для динамической команды проектируется синхронный переход моста и мода на **версию 2**; версия `team.json` остаётся отдельной, равной 1. В A1 константы и схемы не меняются.

Новый протокол передаёт произвольные валидные id, provider, roles, признаки команды, возможности подключения и ревизию. `replyAgentId` не ограничен двумя именами. Для сцены встречи нужен явный `peerAgentId` и проверка обоих агентов, вместо вычисления единственной пары. Архивация должна убирать агента из действующей клиентской модели: определить `agent.remove` с причиной `archived` для живого обновления и полный снимок действующей команды для восстановления связи. Это удаление из клиентского представления, а не физическое стирание истории.

Мост и мод согласуют версию при подключении. При несовпадении — понятное сообщение с обеими версиями и требованием обновления, без частичного применения состава и отправки управляющих команд. Одновременно обновляются Java DTO/разбор сообщений, TS-схемы, генератор документации, утилиты подключения, MCP-клиент планирования и пакет. Повторное подключение по полному снимку должно удалять устаревших NPC, восстанавливать действующих и сохранять исторические записи об архивных агентах.

## 9. Перенос нашей команды и переносимая установка

Перенос идемпотентный, выполняется при остановленной очереди и после проверки отсутствия активных операций. Резервная копия включает состав, задачи/сессии, личности, указатели подключений и игровые настройки; она локальная и не попадает в пакет. Сначала проверить все ссылки и подготовить новые файлы, затем переключить версию согласованно. При ошибке оставить прежнюю конфигурацию и понятное сообщение; повтор не создаёт агентов-дубликатов.

| Прежний ключ | Новая запись |
| --- | --- |
| `marlow` | Тот же id; `provider=codex`, `roles=[developer]`. Сохранить реальное имя, внешний вид, личность, флаги, историю, места и текущую Desktop-привязку в отдельной конфигурации этого агента. |
| `wren` | Тот же id; `provider=claude`, `roles=[planner, reviewer]`. Сохранить имя Клава либо установленное пользователем имя, её внешность, память, инструкции, доступ к проектам и существующий разговор. |
| `juniper`, `kit`, `rowan`, `tove` | Ненастроенные стандартные персонажи не включаются в новую действующую команду. Исторические записи, если они существуют, сохраняются. Если обнаружены реальные назначения, личные данные или подключения, не терять их: показать в отчёте переноса и запросить решение вместо молчаливого удаления. |

В старых данных ключи не переименовываются по всему хранилищу: это сохраняет ссылки задач, памяти и игровых мест. Папку уже существующего общего разговора Клавы можно оставить через проверенный указатель подключения; перенос не должен копированием создать второго владельца того же разговора. Общий файл Codex переносится только в привязку `marlow`, не во все новые Codex.

После переноса — очередь на паузе, проверки обоих подключений без отправки модельных задач, отчёт о сохранённых данных. Продолжение работы — отдельное действие пользователя. Откат восстанавливает совместимые мост/мод и резервную копию профиля; старый мост не должен читать новую схему как старую.

Чистый пакет создаёт пустую команду и предлагает добавить агента мастером настройки. Не копирует наш `team.json`, разговоры, ключи, память, инструкции двух наших проектов, абсолютные пути и пользовательские схемы построек. Общие нейтральные шаблоны и собственные параметры установки пользователя отделены от исполняемых файлов. Minecraft, Fabric и нужные клиентские средства провайдеров проверяются мастером; установка пакета не означает автоматически готовую авторизацию.

## 11. Приёмка следующих этапов и согласование

Для будущей реализации обязательны проверки:

- Два Codex и два Claude: разные разговоры, память, отчёты, паузы, внешность и места; коллизия сессии отклоняется.
- Каждый провайдер проходит все три роли через заявленный адаптер; неподдерживаемые комбинации не выдаются за рабочие. Claude-разработчик сохраняет policy-проверки; Codex-ревьюер возвращает структурированный результат через отдельное действие.
- Явные назначения, автовыбор, отсутствие подходящего агента, несколько ролей, запрет самопроверки и явное «Без ревью».
- Одна очередь между проектами и провайдерами; прямое сообщение при занятом проекте доставляется с подсказкой, не создавая второй запуск очереди.
- Изменение HEAD/рабочей копии, просроченный report, повтор report, смена подключения, остановка и перезапуск моста не дают ложного успеха.
- Архив/восстановление с прежним id; исторические задачи не теряют автора; неподтверждённая остановка не удаляет работающего агента.
- Миграция marlow/wren и нестандартного старого состава, повтор миграции, ошибка в файле и откат сохраняют пользовательские данные.
- Несовпадающие версии мода/моста дают понятный отказ; после переподключения нет лишних NPC.
- Чистая установка в отдельную папку работает без наших профилей и путей; обновление сохраняет настройки. Проверка не запускает реальные задачи и не переносит учётные данные.

Для **A1** достаточно сверки документа с исходниками, проверки целостности JSON-примера, ссылок/путей и отсутствия изменений исполняемого кода. Перечисленные выше проверки функций должны выполняться при реализации, а не отмечаться пройденными сейчас.

A2 согласован пользователем через пульт. Следующие этапы выполняются отдельными задачами; коммит, завершение карточки и автоматическое ревью не разрешают самостоятельно запускать следующую задачу.
